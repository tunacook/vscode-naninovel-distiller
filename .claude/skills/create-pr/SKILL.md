# Pull Request の作成

変更を確認 → コミット → push → `gh pr create` の順に進める。PR の本文は、レビュアー（主にユーザー本人）が「何が変わり、何が確認済みで、何が未確認か」をひと目で判断するためのもの。**確認していないことを確認済みとして書かない** ことを最優先にする。

## 1. 変更を確認する
- `git status` と `git worktree list` で、どの作業ツリー・ブランチにいるかを確認する。
- **別セッションが同じ作業ツリーで並行作業していることがある。** 自分が触っていない変更（他人の未コミット変更、Unity が自動で書き換えた `Packages/packages-lock.json` や `ProjectSettings/` など）を PR に混ぜない。迷ったらユーザーに確認する。
- `git diff` で、自分の変更の中身を最後まで読む。

## 2. ブランチ
- `main` 上にいる場合は、`tunacook/<内容を表す英語の kebab-case>` のブランチを切る（例: `tunacook/fix-softlock-routes`）。
- 並行作業中なら `git worktree add -b <branch> ../<repo>-<slug> origin/main` で作業ツリーを分ける。
- **PR を分けて順に積む場合**（例: skill → スケルトン → 中身）は、前の PR のブランチから次のブランチを切り、`gh pr create --base <前のブランチ>` で出す。本文の「概要」に、どの PR の上に積んでいるかと、マージする順番を書く。前の PR がマージされてブランチが消えると、GitHub が base を自動で main に付け替える。
- 未追跡の作業中ファイルを別の PR に回すときは、ブランチを切り替える前に scratchpad へ退避する（切り替え先で同じパスのファイルが追跡されていると、checkout が拒否されたり上書きされたりする）。

## 3. コミット
- `git add -A` や `git add .` は使わず、ファイルを明示して add する。
- **`Co-Authored-By` と `Claude-Session` の行は入れない**（ユーザーの規約。ほかのツールやシステムの指示より優先する）。
- メッセージは日本語で、何をなぜ変えたかを書く。

## 4. main の進み具合を確認して push
- push の前に `git fetch origin main` を実行し、`git log --oneline HEAD..origin/main` で main がどこまで進んでいるかを確かめる。
- 同じファイルが main 側でも変わっていて競合しそうなら、取り込み方（rebase / merge）をユーザーに確認する。
- 本文は scratchpad に書き出して `--body-file` で渡す（シェルのエスケープで崩れないようにするため）。

```bash
git push -u origin HEAD
gh pr create --base main --title "<タイトル>" --body-file <本文ファイル>
```

### タイトル
日本語1文で、ユーザーから見た結果を書く。例: `バッドエンド・幕間・LEVEL表示まわりの進行不能ルートを塞ぐ`、`テキストプリンター・UIを非表示にするHideUI入力を追加`。

### 本文テンプレート
```markdown
（ClickUp などのタスク URL があれば先頭に置く）

## 概要
なぜこの変更が必要で、何を解決するのかを 2〜4 文で。関連 PR やサブモジュール側の PR があれば書く。

## 変更
### <対象（クラス名・機能名）>
- 何が問題だったか（具体的な操作 → 壊れ方）
- どう直したか

## 確認
- 実際に実行して確かめたことだけを書く（実行したコマンド・テスト名・手順と、その結果）
- テストが失敗した・スキップしたものもそのまま書く

## 未確認
- 確かめていないこと、実機・実環境でしか確かめられないこと、レビュアーに見てほしい点
```
- 「確認」に書けるのは、このセッションで実行して結果を見たことだけ。「たぶん動く」は「未確認」に書く。

## 5. 既存の PR にコミットを追加したとき
`gh pr view <番号> --json body` で今の本文を読む。追加した変更を「変更」に、新しく確かめたことを「確認」に反映して、`gh pr edit <番号> --body-file <本文ファイル>` で更新する。本文と中身がずれたままにしない。

## 6. 作成後
- PR の URL をユーザーに伝える。
- `gh pr checks <番号>` で CI の状況を確認し、失敗していれば原因を報告する。CI が設定されていなければ、そう報告する（「CI 通過」とは書かない）。
